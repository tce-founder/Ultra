# The analytic path

Python, not prose. The rest of this repository is qualitative; the parts of ultrarunning that are
arithmetic — how many grams over how many hours, how many weeks of progression to get there — are
here, so they are re-runnable rather than embedded in a sentence with a number in it.

```
inputs.py    Input / Derived — value + unit + population + source + grade, bound together
fueling.py   race fuelling arithmetic, the fallback ladder, gut-training progression
```

Run it: `cd advisory/model && python3 fueling.py`

No dependencies. Python 3.9+.

## Known weaknesses — read before citing anything

**1. The greedy hourly plan is not optimal and is not meant to be.** It picks the largest items
first, which in the worked example produces a plan that is 83% water-dependent — and then warns
about exactly that. A plan an athlete can remember beats a plan three grams closer to a target that
was itself an estimate. If you want a different composition, reorder the product list.

**2. There is no fluid model, deliberately.** The consensus recommendation is drink-to-thirst, and a
millilitres-per-hour number generated by a program is precisely the scheduled-drinking behaviour
identified as the mechanism of exercise-associated hyponatremia. Sodium is reported per hour as
*information*. Adding a fluid target to this module would be a regression, not a feature — see
`advisory/kb/frameworks/drink-to-thirst.md`.

**3. `gut_training_schedule` uses a +10 g/h per week convention that no trial establishes.** What is
established is that intestinal adaptation occurs and can be fast. The schedule is coaching
convention, repeated across commercial sources. Treat the *shape* as transferable and the step size
as a guess.

**4. The module cannot tell you your rate.** It takes one. The rate comes from what the athlete has
tolerated in training, recorded. Passing in 120 because a trial used it is the misuse the
`population` field on every `Input` is trying to make visible, and it will not stop you.

**5. Nothing here models heat, altitude, night, or intensity** — all of which move gut tolerance,
some of them a lot. A plan that works at 15 °C is not a plan for 32 °C, and this module does not
know the difference.

**6. `Derived` propagates the weakest grade and nothing propagates the weakest *population*.** That
is a real hole. In the worked example the plan inherits UNVERIFIED from the duration estimate, which
is correct; it does not inherit "laboratory cyclists in efforts far shorter than this one" from the
target rate, which it arguably should. Recorded rather than fixed, because it is not obvious what
combining two populations should produce.

## What the worked example is actually demonstrating

Not the fuelling plan. The two lines at the end:

- The total is graded **UNVERIFIED**, and the input that dragged it there is the **race duration** —
  the athlete's own guess. Not the fuelling target, which everyone treats as the uncertain part. The
  weakest link is routinely the one nobody thinks of as a figure at all.
- The only **VERIFIED** number is the athlete's tolerated rate, and it sits 20 g/h below the plan.
  That gap is a gut-training block, and a plan that does not name it has assumed it away.

Both are visible because the grades travel with the numbers. That is the whole argument for the
type.

## `projection.py` — cutoff feasibility

```
python3 projection.py          # sensitivity table
python3 projection.py 14:30    # project from a known Heartbreaker time
```

Projects a Hellbender time from the athlete's March 2026 Mount Mitchell Heartbreaker — same start
line, much of the same terrain, so it is the most informative data point available for the only
question that can invalidate the whole plan: **is 40 hours comfortable, or is it the objective?**

### Known weaknesses

**1. There is no validated model for 50-to-100-mile scaling on mountain terrain.** The method is a
convention. Hence: every output is a range, never a number; the range comes from varying the two
assumptions that matter (vert equivalence, fatigue exponent); and the night penalty is **additive
and separate**, because a daylight 50 contains no night and folding that into an exponent hides
the single biggest difference between the two events.

**2. The grade is UNVERIFIED no matter how well the input time is known**, because the method is.
This is enforced rather than stated: the method is passed to `derive()` as an explicit UNVERIFIED
`Input`. The first version only passed the athlete's time, so the midpoint printed REPORTED while
a note three lines below claimed everything was UNVERIFIED — the exact grade laundering this
repository exists to prevent, committed in the file that teaches the rule.

**3. Breakpoints are computed, not asserted.** The first version hardcoded "somewhere around
13-14 h" in prose sitting directly under a table showing inside-all-assumptions through 15h00.

**4. It cannot see the athlete.** Nineteen months, an injury, seven months off and a rebuild sit
between the input and the target. The projection treats the Heartbreaker runner and the May runner
as the same person, which is the largest unmodelled term and is not small.

**Use the spread to decide, never the midpoint.**
